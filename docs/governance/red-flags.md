# علائم خطر (Red Flags)

**نقش:** Governance — قانون رفتاری سیستم
**وضعیت:** فعال

دیدن هر Red Flag به معنای شکست نیست، فرصتی برای اصلاح زودهنگام است. **قانون طلایی: اگر ۳ یا بیشتر Red Flag همزمان دیدی، STOP و بازطراحی کن.**

---

## دسته ۱: نقض مرزهای ماژول

**Guessing Module** — یک ماژول داده‌ی مفقود را "اختراع" می‌کند (مثلاً اگه `camera` نبود، خودش فرض می‌کند Medium Shot). داده‌ی الزامی/ساختاری هرگز نباید حدس زده شود؛ اگر مفقود است باید Validation جلویش را بگیرد. (استثنا: پیش‌فرض هوشمند برای جزئیات *قابل‌استنباط از Context*، مثل انتخاب خودکار outfit، Red Flag محسوب نمی‌شود — طبق `AI_Governance`.)

**God Module** — یک ماژول کارهای چند ماژول دیگر را انجام می‌دهد (مثلاً PromptEngine هم Validate می‌کند، هم Conflict را حل می‌کند، هم Format می‌دهد). هر مسئولیت باید به ماژول خودش برگردد.

**Chatty Modules** — دو ماژول با هم بیش‌ازحد رفت‌وبرگشت داده دارند (Coupling بالا). راه‌حل: یک Interface واضح با ۱-۲ بار تبادل داده.

**Leaky Abstraction** — جزئیات داخلی یک ماژول مستقیم به بیرون نشت می‌کند (مثلاً کد بیرونی مستقیم `dna.internal_state.color_palette.type` را می‌خواند). راه‌حل: API واضح مثل `dna.hasMutedPalette()`.

---

## دسته ۲: نقض جریان داده

**Circular Dependency** — A به B، B به C، C به A وابسته است. باید یکی از وابستگی‌ها قطع یا معکوس شود.

**Backward Data Flow** — داده از لایه‌ی پایین به لایه‌ی بالا برمی‌گردد (مثلاً OutputComposer مستقیم به SceneEngine وابسته شود). معماری باید یک‌طرفه بماند؛ برای ارتباط معکوس از Event/Callback استفاده شود.

**Hidden State** — یک ماژول state مخفی نگه می‌دارد که در API مستندش نیست. همه‌ی state باید مستند و قابل‌دسترس باشد.

---

## دسته ۳: اعتبارسنجی و مدیریت خطا

**Silent Failures** — خطا رخ می‌دهد ولی سیستم بی‌صدا ادامه می‌دهد. هر خطا باید Log شود یا به کاربر نشان داده شود.

**Validation That Fixes** — Validation به‌جای گزارش خطا، خودش داده را اصلاح می‌کند. Validation فقط باید بگوید چه چیزی غلط است.

**No Error Context** — خطا بدون جزئیات کافی (`"Invalid"` بدون گفتن کدام فیلد/چرا). خطا باید دقیقاً بگوید چه چیزی نامعتبر است و مقدار مجاز چیست.

---

## دسته ۴: Performance

**N+1 Query Problem** — برای N آیتم، N+1 بار پرس‌وجوی جداگانه (به‌جای Batch Loading).

**No Caching** — هر بار محاسبات سنگین از صفر تکرار می‌شود بدون Cache.

**Blocking Operations** — عملیات طولانی، رابط کاربری را فریز می‌کند؛ باید Async/Debounce شود.

---

## دسته ۵: سوءاستفاده از Human Override

**Override as Default** — اکثر عملیات با Override انجام می‌شود، نه با قوانین عادی (مثلاً ۸۵٪ عملیات Override دارند). یعنی سیستم اصلی کار نمی‌کند و کاربر دارد دورش می‌زند — نیاز به اصلاح معماری دارد، نه توجیه بیشتر برای Override زدن.

**Undocumented Override Scope** — Override بدون ثبت خودکار این‌که چه‌چیزی/کجا/چه‌مقداری تغییر کرد. توجه: نبودِ **دلیل** (که اختیاری است) Red Flag نیست؛ آنچه واقعاً مشکل‌ساز است نبودِ ثبت خودکار **Scope** است، چون بدون آن State & Versioning نمی‌تواند تاریخچه را نشان دهد.

```json
// درست:
{ "active": true, "field": "camera.angle", "original_value": "eye-level",
  "override_value": "dutch-angle", "reason": null }
```

**Stale Unreviewed Override** — Override ای که مدت‌هاست فعال است و کاربر هرگز به آن برنگشته تا بررسی کند آیا هنوز لازم است. (این اپ Expiration خودکار ندارد؛ کاربر خودش تصمیم می‌گیرد Revoke کند یا نگه دارد — یک یادآوری دوره‌ای اختیاری می‌تواند کمک کند.)

---

## دسته ۶: تست

**No Tests** — ماژول بدون هیچ تستی. حداقل ۷۰٪ Coverage توصیه می‌شود.

**Tests That Always Pass** — تستی که هیچ‌وقت واقعاً چیزی را بررسی نمی‌کند (`expect(true).toBe(true)`).

**Integration Tests Only** — فقط تست یکپارچگی هست، تست واحد نیست؛ وقتی چیزی خراب شود، معلوم نیست کدام بخش مقصر است.

---

## دسته ۷: مستندسازی

**Code is Documentation** — فرض این‌که "کد خودش واضحه، نیاز به توضیح نیست". بعد از چند ماه حتی خودت هم یادت می‌رود چرا.

**Outdated Documentation** — مستندات با کد واقعی هماهنگ نیست؛ این از نبود مستندات هم بدتر است.

**No Why, Only What** — مستندات فقط می‌گوید کد چه کاری می‌کند، نه چرا این‌طور طراحی شده.

---

## دسته ۸: انحراف معماری

**"Just This Once"** — نقض یک قانون با توجیه "فقط همین یک‌بار". این الگو معمولاً تبدیل به عادت دائمی می‌شود؛ یا قانون را رسماً تغییر بده، یا نقضش نکن.

**Copy-Paste Code** — منطق یکسان در چند جای مختلف تکرار شده؛ باید در یک تابع مشترک جمع شود.

**Magic Numbers** — عدد hardcode بدون توضیح (مثلاً `if (duration > 42)`). باید به‌عنوان ثابت نام‌گذاری‌شده با توضیح تعریف شود.

## چک‌لیست

**قبل از هر Commit:**
- [ ] هیچ ماژولی حدس نمی‌زند
- [ ] هیچ Circular Dependency نیست
- [ ] همه‌ی خطاها Log می‌شوند
- [ ] Test Coverage قابل‌قبول است
- [ ] مستندات به‌روز است

**قبل از هر مرحله‌ی بزرگ (Deploy معادل):**
- [ ] هیچ God Module نیست
- [ ] همه‌ی Override ها Scope خودکار ثبت‌شده دارند (دلیل اختیاری است)
- [ ] Performance قابل‌قبول است
- [ ] هیچ "Just This Once" باقی نمانده

**بازبینی دوره‌ای:**
- [ ] نرخ استفاده از Override پایین و منطقی است
- [ ] تکرار کد کم است
- [ ] مستندات تازه است
- [ ] Override های قدیمی حداقل یک‌بار بازبینی شده‌اند

---

## واکنش اضطراری

- **۳+ Red Flag بحرانی همزمان:** توقف → بازبینی → بازطراحی → تست → ادامه
- **۵+ Red Flag سطح بالا:** توقف → گفتگو با معمار پروژه → بازطراحی → پیاده‌سازی → تست
- **۱۰+ Red Flag هر سطحی:** توقف → بازبینی کامل معماری

**یادآوری نهایی:** دیدن Red Flag فرصت است، نه شکست. اگر چیزی غیرعادی به‌نظر می‌رسد، احتمالاً هست.
