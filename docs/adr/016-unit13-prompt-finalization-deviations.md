# ADR-016: تصمیمات پیاده‌سازی واحد ۱۳ (Prompt Finalization Pipeline) — لایه‌ی دامنه

**تاریخ:** 2026-07-20
**وضعیت:** تمام تصمیمات مستقل (طبق دستور کار: جزئیات پیاده‌سازی محلی، نه سؤال معماری)

## Context

پیاده‌سازی لایه‌ی دامنه‌ی خالص واحد ۱۳ (Prompt Finalization Pipeline) طبق `docs/blueprints/13-prompt-finalization.md` — آخرین حلقه‌ی جاافتاده‌ی Pipeline اصلی، بین Renderer (واحد ۱۴، بخش الف) و Output Composer (واحد ۱۴، بخش ب). `RenderedOutput` و `ModelProfile` از `domain.outputdelivery` (واحد ۱۴، از قبل پیاده‌شده) import شدند — تأیید شده با grep، بدون تغییر آن فایل‌ها.

## تصمیم مستقل ۱: پیاده‌سازی واقعی Phase 3-5 (نه کامنت جای‌گذار)

کد مفهومی بلوپرینت خودش صریحاً می‌گوید «Phase 3-5: Stop words, compression, grammar (پیاده‌سازی کامل در کد واقعی)» — طبق دستور صریح این قدم، این سه فاز واقعاً پیاده شدند:

- **Phase 3 (Stop Words Filtering):** لیست `STOP_WORDS = ["a", "the", "very", "that", "just", "really", "quite"]` — دقیقاً همان کلمات نمونه‌ی بلوپرینت («very very, a, that») به‌علاوه‌ی چند کلمهٔ پرکنندهٔ رایج مشابه (just, really, quite) که خودِ دستور این قدم پیشنهاد داده بود. `filterStopWords` هر رخداد این کلمات را با `\b<word>\b` (Case-insensitive) حذف می‌کند — همان الگوی Regex که `removeSynonymDuplicates` بلوپرینت از قبل استفاده کرده بود، برای هم‌راستایی سبک.
- **Phase 4 (Token Optimization):** طبق پیشنهاد صریح دستور کار، فقط حذف فاصله‌های اضافه (`\s+` → یک فاصله + trim) — یک «فشرده‌سازی بدون از دست دادن معنی» واقعاً محافظه‌کارانه. فشرده‌سازی معنایی واقعی (پارافریز/کوتاه‌سازی جمله) نیازمند یک مدل زبانی یا الگوریتم summarization است که خارج از این پیاده‌سازی محلی است.
- **Phase 5 (Final Polish):** حروف بزرگ ابتدای جمله (`replaceFirstChar { it.uppercase() }`) + افزودن نقطه‌ی پایانی اگر جمله با `.`/`!`/`?` تمام نشده باشد — دقیقاً طبق پیشنهاد صریح دستور کار.

**`stopWordsRemoved` واقعی محاسبه می‌شود** (نه هاردکد `0` مثل کد مفهومی بلوپرینت): تعداد رخدادهای واقعی کلمات `STOP_WORDS` قبل از حذف شمرده می‌شود.

## تصمیم مستقل ۲: محدودیت زبان انگلیسی حفظ شد (طبق تصریح بلوپرینت + ADR-015)

بلوپرینت خودش صریحاً می‌گوید این منطق «فقط برای متن انگلیسی طراحی شده؛ معادل فارسی هنوز تعریف نشده — محدودیت شناخته‌شده». این با ADR-015 (واحد ۱۴) هم‌راستاست: `render()` فعلاً همیشه `RenderedOutput.language = "en"` تولید می‌کند. معادل فارسی این منطق پیاده نشد — دقیقاً طبق دستور صریح این قدم.

## تصمیم مستقل ۳: دو Rule «ساختاری/پردازشی» با تابع واقعاً تست‌پذیر پیاده شدند

### `validateConflictsResolved` (نه یک تابع همیشه-null)
Rule «تضاد آب‌وهوا/منطقی تشخیص داده شود → باید حل شود» در بلوپرینت با برچسب «Blocking (پردازشی، نه Validation کاربر)» آمده — یعنی `cleanPrompt` خودش این تضاد را حل می‌کند، نه این‌که کاربر را متوقف کند. به‌جای یک تابع که چون منطق داخلی خودش تضمین می‌کند همیشه `null` برمی‌گرداند (بی‌فایده برای تست)، `validateConflictsResolved(cleanedText: String)` روی **متن نهایی** دوباره `detectConflicts` را اجرا می‌کند — این واقعاً تست‌پذیر است، چون اگر کسی `cleanPrompt` را با `options.detectConflicts=false` صدا بزند، این تابع همچنان تضاد باقی‌مانده را تشخیص می‌دهد (تست شده).

### `validateCompressionRatio`
Rule «کاهش طول کمتر از ۳۰٪» مستقیم روی `CleaningReport.compressionRatio` با آستانه‌ی پیش‌فرض `0.3f` (دقیقاً طبق مثال بلوپرینت) پیاده شد.

### Rule «نقض بسته‌بندی» و «Hardcode در UI» (خارج از این واحد)
این دو Rule به بخش ب/ج واحد ۱۴ تعلق دارند، نه واحد ۱۳ — قبلاً در ADR-015 مستند شده‌اند.

## تصمیم مستقل ۴: طراحی امضای تابع پل‌زننده `finalizePrompt`

```kotlin
fun finalizePrompt(
    rendered: RenderedOutput,
    profile: ModelProfile,
    options: CleaningOptions = CleaningOptions()
): Pair<RenderedOutput, TokenCheckResult>
```

دقیقاً امضای پیشنهادی خودِ دستور کار. دلایل هر انتخاب:

- **ورودی/خروجی `RenderedOutput` واقعی واحد ۱۴ (نه یک نوع محلی جدید):** خروجی این تابع باید مستقیماً در لیست `renderedOutputs` که به `composeOutput` واحد ۱۴ داده می‌شود قابل استفاده باشد، بدون تبدیل میانی — همان چیزی که ADR-015 از قبل پیش‌بینی کرده بود («renderedOutputs از بیرون تزریق می‌شود، چه خام از render()، چه بعداً Clean‌شده»).
- **`.copy(formattedPrompt = cleanedText)`:** فقط متن تغییر می‌کند؛ `modelProfileId`/`language` دست‌نخورده می‌مانند — Cleaning هدف مدل را عوض نمی‌کند، فقط متن را.
- **`TokenCheckResult` جداگانه، نه فیلد اضافه روی `RenderedOutput`:** طبق بلوپرینت ۱۴، `RenderedOutput` دقیقاً سه فیلد دارد. افزودن فیلد به آن نوع، ویرایش فایل‌های واحد ۱۴ است — که این قدم صریحاً منع کرده («تغییر فایل‌های واحد ۱۴ — فقط مصرف»). پس `Pair<RenderedOutput, TokenCheckResult>` هر دو نتیجه را بدون دست‌زدن به واحد ۱۴ برمی‌گرداند.
- **`CleaningReport` میانی نگه داشته نمی‌شود:** `finalizePrompt` فقط متن نهایی و نتیجه‌ی توکن را لازم دارد تا به `composeOutput` وصل شود؛ در صورت نیاز به جزئیات تمیزکاری (مثلاً برای UI/Log)، `cleanPrompt` مستقیماً قابل فراخوانی جداگانه است. این یک تصمیم سادگی عمدی است (بدون افزودن یک `Triple`/نوع جدید برای چیزی که این تابع پل‌زننده لازم ندارد).

## Consequences

- **آسان می‌شود:** Pipeline اصلی از واحد ۱۱ (PromptBlueprint) تا واحد ۱۴ (Output Composer) اکنون کامل و بدون حلقه‌ی جاافتاده است — `render()` → `finalizePrompt()` → `composeOutput()` یک زنجیره‌ی واقعی و قابل کامپایل است.
- **بدهی باقی‌مانده:** معادل فارسی Prompt Cleaner پیاده نشده (منتظر تصمیم معماری درباره‌ی زمان افزودن پشتیبانی چندزبانه به خروجی خام)؛ Budget Tracking/Cost Estimation طبق بلوپرینت پیاده نشد (فیچر اختیاری، خارج از Scope اصلی).
