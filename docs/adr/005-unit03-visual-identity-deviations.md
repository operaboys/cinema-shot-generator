# ADR-005: تصمیمات پیاده‌سازی واحد ۰۳ (Visual Identity) — لایه‌ی دامنه

**تاریخ:** 2026-07-19
**وضعیت:** بخشی تأییدشده (توسط کاربر در جریان این قدم)، بخشی سؤال باز برای معمار

## Context

پیاده‌سازی لایه‌ی دامنه‌ی خالص واحد ۰۳ (Style Matrix + Cinematic Language) طبق `docs/blueprints/03-visual-identity.md`. این واحد صاحب اصلی `CinematicMode` است — enum ای که واحد ۰۷ قبلاً به‌صورت موقت `String` گرفته بود (`docs/adr/004-unit07-validation-consistency-deviations.md`، تصمیم ۱).

## تصمیمات تأییدشده

### ۱. Rule 2 بخش ب از ValidationIssue سراسری واحد ۰۷ استفاده می‌کند (تأییدشده توسط کاربر)
**مشکل:** `validateShotDurationForCinematicMode` نیاز به یک نوع خروجی برای Warning داشت. بلوپرینت ۰۳ خودش هیچ نوع Kotlin ای برای این پیشنهاد نکرده بود (برخلاف بخش الف که `CompatibilityResult` دارد).
**گزینه‌ها:** (الف) استفاده از `ValidationIssue`/`Severity` واحد ۰۷ (قبلاً پیاده‌سازی‌شده)؛ (ب) ساخت یک نوع محلی پنجم (مثل واحدهای ۰۱/۰۲/۰۶/۰۷).
**تصمیم (تأییدشده):** گزینه‌ی الف. این **اولین وابستگی واقعی بین دو پکیج domain** در کل پروژه است (`domain.visualidentity` → `domain.validation`).
**چرا:** برخلاف رابطه‌ی واحد ۰۷ → واحد ۰۳/۰۵ (که در آن زمان واحدهای مقصد هنوز وجود نداشتند و وابستگی به کد آینده بود)، اینجا واحد ۰۷ از قبل پیاده و پایدار است؛ استفاده از نوع سراسری‌اش برای کد **جدید** به‌جای ساخت نوع محلی ششم، دقیقاً همان هدفی است که بلوپرینت ۰۷ برای `ValidationIssue` تعریف کرده بود. اضافه‌کردن یک نوع محلی دیگر وضعیت «۴ نوع ValidationResult محلی» که در ADR-004 نگران‌کننده اعلام شده بود را بدتر می‌کرد.

## تصمیمات مستقل (بدون نیاز به تأیید جداگانه، طبق اصول تثبیت‌شده)

### ۲. checkStyleCompatibility — رفتار حداقلی حفظ شد (بدون افزودن قوانین نمونه)
بلوپرینت «نمونه قوانین» (Oil Painting+8K→LOW، Ghibli+Watercolor→HIGH) را فقط در کامنت آورده، نه به‌عنوان مشخصات واقعی برای پیاده‌سازی؛ تابع خودش صراحتاً همیشه `MEDIUM/false` برمی‌گرداند. افزودن این «نمونه‌ها» به‌عنوان قانون واقعی یعنی اختراع یک ماتریس سازگاری کامل که هیچ منبع دیگری آن را مشخص نکرده — طبق قانون «بدون حدس زدن»، رفتار حداقلی دقیقاً طبق بلوپرینت حفظ شد.

### ۳. StyleMatrix / CustomStyle — data class افزوده (نه در فهرست صریح دستور کار)
Rule 1/2/3 نیاز به یک ظرف داده برای «سبک اصلی/ثانویه‌ی فعلی» داشتند؛ بلوپرینت این را در بخش «ساختار داده» (JSON) نشان داده بود ولی در کد مفهومی نیاورده بود. مشابه تصمیمات افزودنی واحدهای ۰۲ (OverrideRules) و ۰۶ (Hair/FacialFeatures/Environment)، این دو data class برای تکمیل ساختار لازم اضافه شدند.

### ۴. Rule 1 بخش الف بدون تابع Runtime — تضمین در سطح Type System
`StyleMatrix.primaryStyle: StyleReference` غیر-nullable است؛ مشابه تصمیم Rule 2 واحد ۰۶ (ADR-003 §۷)، این الگو دوباره استفاده شد.

### ۵. Rule 3 بخش الف — `StyleUpdateResult` محلی (Allowed/Blocked)
`validatePrimaryStyleUpdate(newPrimaryStyle: StyleReference?)` مقدار پیشنهادی به‌روزرسانی را می‌گیرد؛ `null` یعنی تلاش برای حذف. نوع محلی جدید (نه بازاستفاده از `UpdateResult` واحد ۰۶) برای پرهیز از وابستگی غیرضروری `domain.visualidentity` → `domain.asset`.

### ۶. `parseCinematicMode`: نگاشت "hybrid" → `BALANCED`
ساختار JSON بلوپرینت برای `global_mode` مقدار `"hybrid"` را نشان می‌دهد، اما enum مفهومی همان بخش نام سومین مقدار را `BALANCED` گذاشته (نه `HYBRID`) — یک ناهماهنگی واژگانی جزئی درون خودِ بلوپرینت. چون enum صراحتاً `BALANCED` است و پیام تابع Rule 2 هم به همین enum ارجاع می‌دهد، نگاشت `"hybrid" → CinematicMode.BALANCED` منطقی‌ترین تفسیر بود (نه یک ابهام معماری، صرفاً هم‌ترازی واژگانی).

### ۷. determineHybridPacing/getPacingFromEmotion — بلوپرینت کامل بود، نه ناقص
دستور کار احتمال داد که کد `determineHybridPacing` در سند «قطع شده» باشد. بررسی مستقیم فایل (`docs/blueprints/03-visual-identity.md`، خطوط ۱۲۲–۱۴۱) نشان داد امضا و بدنه‌ی هر دو تابع (`determineHybridPacing` و `getPacingFromEmotion`) کامل و بدون علامت قطع‌شدگی حاضرند؛ `git log` هم فقط یک commit برای این فایل نشان می‌دهد. هر دو تابع دقیقاً طبق بلوپرینت پیاده شدند — سؤالی برای معمار مطرح نشد چون داده‌ای برای پرسیدن ناقص نبود.

### ۸. تداخل با واحد ۰۷ (Logic Conflict Checker) — کاری تکراری اینجا انجام نشد
دو مورد از سه تضاد ذکرشده در «تداخل با واحدهای دیگر» (حرکت سریع+Long-take، دوربین ثابت+تعقیب) از قبل در `domain.validation.LogicConflictChecker` (واحد ۰۷) پیاده شده‌اند. سومی (Slow Motion + دیالوگ) در بلوپرینت ۰۳ ذکر شده اما **در بلوپرینت ۰۷ خودش هم پیاده نشده** — این یک شکاف در پیاده‌سازی واحد ۰۷ نسبت به بخش «تداخل» خودش به‌نظر می‌رسد، نه مسئولیت واحد ۰۳. چیزی در این قدم اضافه نشد.

### ۹. توابع non-suspend
مشابه ADR-001 §۵، ADR-002 §۵، ADR-003 §۱۰، ADR-004 §۴.

## سؤال باز برای معمار

آیا واحد ۰۷ باید بعداً پارامترهای `String` در `checkFastMotionLongTake` را به `CinematicMode`/`MotionLevel` واقعی Migrate کند (حالا که واحد ۰۳ صاحب `CinematicMode` را پیاده کرده — `MotionLevel` هنوز منتظر واحد ۰۵ است)؟ این migration در این قدم اجرا نشد.

## Consequences

- **آسان می‌شود:** واحد ۰۷ اکنون می‌تواند مستقیماً از `CinematicMode` واقعی استفاده کند (وقتی migration انجام شود)؛ Rule 2 بخش ب با نوع سراسری از ابتدا سازگار است، نه یک نوع محلی که بعداً باید Migrate شود.
- **بدهی ثبت‌شده:** پیشنهاد Migration واحد ۰۷ به `CinematicMode` واقعی (باز)؛ شکاف «Slow Motion + دیالوگ» در واحد ۰۷ (باز، مسئولیت آن واحد)؛ همچنان ۴ نوع ValidationResult محلی قدیمی (۰۱/۰۲/۰۶) بدون تصمیم Migration (ADR-004، هنوز باز).
